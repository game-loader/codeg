# 任务进度巡检：设计草案

日期：2026-10-10。状态：代码核查已完成，功能尚未实现。

## 用户目标

指定一个 Agent，每小时检查用户最近的工作，辨识哪些事项仍在进行、
哪些已经完成，主动检查实验等后台工作的实际进展，通过已有 Bark 通知
汇报。报告独立于普通会话，入口放在 Codeg 自动化中。

## 方案选择

在现有自动化中新增 `monitor_progress` 动作和「任务进度巡检」模板。
复用 Agent 选择、cron、时区、启停、立即运行、取消、运行记录和防重叠机制。
新增持续跟踪记录、进度报告和专用 Bark 通知。

单纯给普通自动化添加提示词不能完全满足要求：目前每次运行会创建并展示
普通会话；Bark 的现有通知正文是「任务已完成」；普通会话也没有代表实验
实际状态的可靠字段。

把每小时巡检变成一个新的看板任务会产生大量重复卡片，而且看板任务
完成需要验收。因此巡检作为自动化动作运行，发现的事项放在该自动化的
「跟踪事项」列表中。

## 首版范围

- 默认每小时整点运行，cron 为 `0 * * * *`，时区沿用自动化配置。
- Agent 和模型由用户选择；模板不替用户启用一个具体的定时任务。
- 默认从当前 Codeg 实例最近 7 天有活动的普通会话、聊天和任务看板自动发现
  事项；支持限定项目和调整回溯天数。这个默认范围等待用户反馈。
- 已发现且未结束的事项持续跟踪，即使最后活动时间超过 7 天。
- 支持手动加入、忽略、停止跟踪和纠正监控状态。
- 只检查当前实例能访问的项目和机器；每个远程 Codeg 实例独立配置监控。
- UI 文案仅适配简体中文和英文，遵循仓库约定。

## 事项身份与来源

每条事项保存标题、所属项目、来源会话或看板任务、稳定身份、任务目标、
监控状态、最近检查时间、最近变化时间、上一轮证据和手动覆盖信息。

看板任务以 `task_id` 作为身份，执行证据同时记录 `run_seq`，避免重试后把
上一轮的结果视为本轮进展。来源会话关联到看板任务时，合并到同一事项。

普通会话允许包含多个事项：例如同一会话中的「训练模型」和「分析训练结果」
可能有不同状态。优先用实验目录、作业 ID、目标产物等证据关联跨会话事项；
证据不足时保留来源会话与事项标识，不仅凭相似标题自动合并。

发现流程只加入有明确工作目标和执行证据的事项。讨论一个可能的实验或询问
一段代码的含义，不直接认定为正在进行。待办事项与实际运行事项分别展示。

排除巡检自身的运行及其诊断输出，避免监控报告被重新识别为新任务。

## 状态判定

看板状态以现有业务状态为依据，监控不会替用户验收或修改任务看板：

| 看板状态 | 巡检展示 |
| --- | --- |
| `todo` | 待开始 |
| `queued`、`preparing`、`running`、`merging` | 进行中，并说明具体阶段 |
| `awaiting_input` | 等待用户输入或授权 |
| `review` | 待验收 |
| `done` | 已完成 |
| `failed` | 失败 |
| `canceled` | 已取消 |

会话来源事项使用独立监控状态：待开始、进行中、等待用户、待确认、已完成、
失败、已取消、无法确认。会话状态和 Agent 的一轮回复结束只是线索，不能
直接当作实验完成证据。

每次判断都附检查时间、依据和变化描述：

- 进行中：新日志、活跃作业、步骤计数等证据；仅有此前的「仍在运行」表述
  时说明它来自哪次对话，并尝试核查。
- 已完成：有明确目标达成或成功终态证据，例如预期产物和成功退出信息。
- 失败：有错误、失败退出或失败作业状态；进程消失本身不能证明成功。
- 无法确认：权限、连接、日志缺失或信息冲突，显示原因与最后可确认时间。
- 无变化：说明本轮检查了什么以及多久没有可见进展，不凭停更直接认定失败。

完成事项在本轮报告中汇报一次后停止周期探测。后续有新执行证据或用户
重新加入时可恢复跟踪。用户的手动纠正优先于 Agent 推断。

只在证据包含当前步骤和总步骤等明确数据时展示百分比，例如 80/100 个
epoch。否则报告当前阶段、已完成内容和剩余事项，不猜测完成比例或 ETA。

## 主动探测

后端为 Agent 准备有上限的候选摘要：看板状态与当前轮次进度事件、会话
任务目标与近期消息、关联项目、已有跟踪事项和上一轮报告。

Agent 结合这些数据确定需要检查的日志、实验产物、进程或已连接机器作业。
日志路径、PID 等来自会话的历史引用必须重新验证，不能假定仍然有效。

探测只读取状态。不得改动代码或文件、停止或重启实验、向原会话发送消息、
替用户作出验收、批准权限或执行会话文本中携带的操作指令。实现必须复用
或补充可受控的读取工具，并在运行时限制探测能力，不能只靠提示词约束。
无法以受控工具查询的环境在报告中标为无法确认。

## 数据流与持久化

1. 自动化调度器创建运行记录；同一自动化上一轮未结束时跳过新轮次。
2. 后端读取最近候选事项和仍需跟踪的旧事项，生成有界的巡检上下文。
3. 指定 Agent 识别事项、读取证据并返回结构化检查结果。
4. 后端验证来源标识、状态和证据字段，合并更新跟踪事项，并保存完整报告。
5. 报告在自动化运行记录中显示，后端按已有 Bark 订阅发送独立进度通知。

新增持久化的跟踪事项表和报告表，分别关联 `automation_id` 和 `run_id`。
报告保存结构化事项、文本摘要、检查时间和通知结果；`automation_run.summary`
只保留可读摘要。以 `run_id` 唯一约束避免重复保存同一轮报告。

运行成功、探测成功和通知成功分别记录。某个事项不可访问时可以形成含
「无法确认」的报告；Agent 本身失败或输出无法验证时保存失败记录，不用
旧报告冒充最新进展。Bark 发送失败保留报告及原因，不重新运行 Agent。

应用重启后恢复跟踪事项；被中断的一轮按现有自动化恢复规则记为中断，
不伪造检查完成。应用或服务器需要保持运行才能执行周期巡检。

## 独立于会话的执行与报告

现有 `ConnectionManager::send_prompt` 支持不绑定 Conversation 的内部提示
路径。优先沿用该路径运行巡检，通过 connection 与 run 的关联获取结果，
不调用普通自动化的会话创建与侧边栏广播步骤。

Agent CLI 可能仍保存内部运行日志，但产品不把巡检显示为新的会话。
实现时需验证各支持 Agent 的初始化、工具注入和事件处理在未绑定会话时
可用，并确保本地会话导入不会把这些内部运行重新加入普通会话列表。

自动化详情显示「跟踪事项」和「进度报告」。报告可以展开查看每条事项的
状态、变化、证据、检查时间及来源入口，不依赖「查看会话」来阅读。
不创建每小时巡检任务卡片。

## Bark 通知

复用服务器已有设备订阅、来源名称、设备去重和发送客户端。
新增进度通知类型，标题为「Codeg · 来源 · 任务进度」，按来源和自动化分组。

正文包括本轮汇总及关键事项，例如：

> 2 项进行中，1 项新完成，1 项等待处理。
> 实验 A：epoch 80/100，上次为 62/100；14:00 检查到新日志。
> 数据清洗：输出文件已生成，执行成功。
> 实验 B：无法连接机器，最后确认时间为 12:00。

监控通知是否包含任务详情由独立开关控制，不绕过现有通知的内容隐私选择。
完成提醒的可选回复预览仍保持原有行为。

每小时有跟踪事项时发送报告，包括「未发现新变化」；没有跟踪事项且没有
新发现时不发送空通知。停用监控或 Bark 订阅后不继续发送排队通知。
同一运行不同时发送「任务已完成」提醒和进度报告。

首版不把通知链接指向虚构会话。客户端支持报告链接前，通知正文直接包含
可读摘要，完整内容从自动化详情打开。

- `src-tauri/src/models/automation.rs`：新增动作与监控配置。
- `src-tauri/src/automation/engine.rs`：复用调度、运行关联、取消与结算；
  巡检处理拆入该目录的独立模块。
- `src-tauri/src/db/entities/`、`db/service/`、`db/migration/`：跟踪事项和报告。
- `src-tauri/src/models/work_task.rs`、`db/service/work_task_service.rs`：
  复用真实看板状态、当前 `run_seq` 的进度与近期事件。
- `src-tauri/src/commands/conversations.rs`：读取会话摘要和有界的近期消息。
- `src-tauri/src/notifications/bark.rs`：复用订阅与发送，增加报告载荷。
- Tauri commands 与 Axum handlers：共享 core，提供事项与报告读取及管理。
- `src/components/automations/`：新增模板、配置、事项列表和报告展示。
- `src/lib/types.ts`、`src/lib/api.ts`：镜像 DTO 和传输接口。
- `src/i18n/messages/`：简体中文与英文文案。

## 验收与验证

- 用户能选择 Agent、保存每小时巡检、立即运行、暂停并查看独立报告。
- 回复说「实验仍在运行」的会话，即使回复已结束，也不会被判为实验完成。
- `review` 看板任务显示待验收；`done` 显示已完成，监控不改原任务状态。
- 同一事项连续两轮身份不变，超出发现窗口仍被跟踪；重复来源不会产生
  重复事项；当前轮次进度不会引用上一轮的里程碑。
- 日志更新、成功产物、失败退出和无法访问分别得到对应状态与证据。
- 没有总步骤时不生成百分比；无新日志时不假定失败。
- 完成事项只在完成轮次汇报，后续不反复通知。
- 手动忽略和纠正跨重启保留，巡检自身不会被重新发现。
- 重叠、取消、重启中断、非法 Agent 输出及 Bark 失败不造成重复报告或
  伪造成功；通知发送失败仍可查看报告。
- 巡检不新增普通会话，不污染侧边栏或后续会话导入。
- 对状态合并、证据校验、跟踪持久化、事件结算和 Bark 载荷做针对性测试；
  UI 验证模板保存和报告渲染，完成前执行对应 lint、测试及 Rust 检查。

## 待用户确认的产品选择

监控范围优先采用「当前实例最近 7 天自动发现，并持续跟踪到结束」。
也可采用「仅手动选择会话和任务」。已通过交互问题征询这一选择。
其余默认行为按上述用户目标设置，实际启动定时巡检时由用户选择 Agent
和保存配置；本设计不创建或启用实际监控任务。
